# Engineering Review Protocol

## Purpose

This repository is developed as a research-grade and production-oriented Legal AI platform. No material architectural or ML change is considered complete until it has passed automated tests, measured evaluation, and an independent Claude review.

## Required loop

1. **Design**
   - State the problem, expected behavior, constraints, affected contracts, resource impact, security impact, and rollback strategy.
   - Prefer existing modules. Do not create parallel implementations.

2. **Implementation**
   - Make the smallest coherent change.
   - Keep ownership boundaries from `TEAM_OWNERSHIP.md`.
   - Preserve backward compatibility where practical.

3. **Verification**
   - Run focused unit tests.
   - Run lint/type checks for changed code.
   - Run the relevant retrieval/ML benchmark for retrieval, reranking, generation, or model changes.
   - Record latency, memory/VRAM, and cost where the change can affect runtime resources.

4. **Claude review**
   Claude must review the actual diff and repository context, not only a summary. The review must explicitly check:
   - architecture and dependency direction;
   - correctness and edge cases;
   - legal-data integrity and provenance;
   - Arabic-language behavior;
   - retrieval quality and evaluation validity;
   - evidence/citation grounding;
   - security and prompt-injection risks;
   - resource usage and hardware portability;
   - failure handling and observability;
   - test quality and missing regression cases;
   - future scalability and migration risks.

5. **Fix review findings**
   Findings that can cause incorrect legal output, data corruption, security exposure, reliability failure, or measurable regression are blockers. Non-blocking findings may be deferred only when documented.

6. **Final gate**
   A change is accepted only when:
   - tests pass;
   - no protected retrieval metric regresses beyond the documented tolerance;
   - no critical security issue remains;
   - resource behavior is within the declared budget or the budget is intentionally changed and benchmarked;
   - Claude review has been completed;
   - documentation and changelog notes are updated when behavior changes.

## Roles

### Primary engineering review

This assistant owns system-level design, architecture, evaluation strategy, resource engineering, and integration decisions.

### Claude review

Claude acts as an adversarial principal engineer and independent code reviewer. Claude must challenge assumptions and may reject an implementation even when tests pass.

### Human/domain review

Legal-domain decisions, source authority, interpretation of ambiguous legal metadata, and acceptance criteria for legal correctness require human/legal review before being promoted to authoritative production knowledge.

## Evidence policy

Never describe a metric as proof of legal understanding unless the benchmark actually measures legal understanding. Self-retrieval smoke tests are regression tests, not legal reasoning benchmarks.

Never train and evaluate on overlapping examples without an explicit reason and leakage analysis.

Every legal claim generated by the system must remain traceable to retrieved evidence. Unsupported claims must result in an explicit abstention or warning according to policy.

## Failure-learning policy

Production failures must not directly modify code, prompts, models, or legal knowledge.

The controlled loop is:

`Failure -> classify -> contain/recover -> record fingerprint -> create regression case -> investigate -> implement fix -> benchmark -> review -> release`

## Change classes

### Class A — Low risk

Documentation, tests, non-functional refactors, observability additions.

Required: focused tests and Claude review when behavior or architecture is affected.

### Class B — Runtime / infrastructure

Resource policies, concurrency, caching, API lifecycle, packaging, Docker, CI/CD.

Required: tests + resource benchmark where applicable + Claude review.

### Class C — Retrieval / NLP / ML

Normalization, embeddings, BM25, fusion, reranking, query understanding, model routing.

Required: before/after benchmark, latency/resource measurements, regression suite, Claude review.

### Class D — Legal knowledge behavior

Schema, jurisdiction handling, legal versions, amendments, provenance, authoritative source ingestion.

Required: data-quality tests, provenance checks, temporal consistency checks, human/legal review for ambiguous semantics, Claude review.

### Class E — Safety / security critical

Prompt-injection defenses, tenant isolation, secrets, authorization, audit trails, external tool access.

Required: security tests, adversarial tests, Claude review, and explicit sign-off before release.

## Review template for Claude

For every material change, ask Claude to return:

1. **Verdict:** APPROVE / APPROVE WITH CHANGES / REQUEST CHANGES
2. **Critical findings:** correctness, legal integrity, security, reliability
3. **Performance/resource findings:** CPU, RAM, VRAM, latency, concurrency, cost
4. **ML findings:** benchmark validity, leakage, metric interpretation
5. **Architecture findings:** dependency violations, duplication, coupling
6. **Tests missing:** exact tests to add
7. **Regression risks:** likely future breakages
8. **Recommended implementation changes:** concrete file/module level actions
9. **Acceptance checklist:** measurable conditions for merge

## Golden rule

**No impressive code without evidence. No benchmark without a valid test design. No legal answer without traceable evidence. No automatic self-modification in production.**
